# 数智供社 v8533：HTTPS、数据库、微信、CA、支付、物流、发票、监管逐项开通操作卡

本卡适用于当前正式交付线：前台 **v8533**，后端 API **v8530**。它说明“如何逐一打开”真实能力，不把本地演示数据、随机令牌或 `CHANGE_ME` 占位值当成生产资源。

## 先理解两个状态

每项能力都有两个状态，必须同时满足才可以对外放行：

1. **代码已具备**：仓库有路由、校验、幂等、审计和失败闸门。
2. **机构已验收**：真实域名/账号/证书/机构回执/对账证据已经登记。

只满足第 1 项时，接口可以在灰度环境返回“未开通”或 `503`；不能用前端按钮、环境变量或本地假回调绕过第 2 项。

## 0. 先准备一份生产配置

在 API 服务器上执行，输出文件必须是权限 `600`，不要在电脑项目目录或 Git 仓库中保存生产密钥：

```bash
sudo node /opt/shuzhi-v8530/scripts/create-shuzhi-production-env.mjs \
  --output /etc/shuzhi-v8530.env \
  --app-domain app.你的正式域名.cn \
  --api-domain api.你的正式域名.cn
sudo chmod 600 /etc/shuzhi-v8530.env
```

随后只在服务器的密钥管理系统或受限环境文件中填写真实值。必须先填：

- `SHUZHI_RUNTIME_MODE=production`
- `SHUZHI_DB`、`SHUZHI_BACKUP_DIR`、`SHUZHI_BACKUP_RETENTION_DAYS`
- `SHUZHI_API_TOKEN`、`SHUZHI_ADMIN_TOKEN_ROLES`
- `SHUZHI_ALLOWED_ORIGIN=https://app.你的正式域名.cn`
- `VITE_API_BASE=https://api.你的正式域名.cn`

微信、CA、支付、物流、发票、监管的 `READY` 先保持 `false`。配置文件不应出现 `CHANGE_ME`、`local-demo-token` 或前端令牌。

后端自身也会在生产启动时拒绝非 HTTPS 根 CORS 来源，以及已标记 `READY=true` 但没有 HTTPS 机构适配器根地址的配置；不能只依赖启动前检查脚本。

## 1. 开通 HTTPS API（先做）

### 外部要开通的资源

- 已实名的正式域名；大陆服务器按要求完成备案。
- API 服务器（CVM/轻量/容器均可）和安全组：公网只开放 80/443，数据库端口不开放公网。
- TLS 证书；`api` 域名证书的 SAN 必须覆盖正式 API 域名。

### 部署顺序

1. DNS 将 `api.你的正式域名.cn` 指向 API 服务器。
2. 用 `npm run render:shuzhi-nginx -- --api-domain ... --tls-dir ...` 渲染 API-only Nginx 配置。
3. Nginx 监听 443，80 只做 301；反向代理到 `127.0.0.1:8787`。
4. CORS 只允许精确的 `https://app.你的正式域名.cn`，不能使用 `*`。
5. 验收：

```bash
curl -fsS https://api.你的正式域名.cn/health/live
curl -fsS https://api.你的正式域名.cn/health/ready
curl -fsS https://api.你的正式域名.cn/api/v1/platform/capabilities
```

### 放行证据

记录证书链/TLS 扫描、DNS、CORS 预检和三个接口的回验结果，在 `SHUZHI_HTTPS_ACCEPTANCE_REF` 登记证据编号。证据未登记时，不进入正式交易。

## 2. 开通生产数据库和备份

当前 v8533 首批灰度使用受保护的云硬盘 SQLite；`local-backend` 使用 Node `node:sqlite`，不能把 MySQL/PostgreSQL 连接串直接填入 `SHUZHI_DB`。规模化前必须另行完成 repository 迁移、连接池和恢复演练。

1. 在独立云硬盘创建 `/var/lib/shuzhi-v8530/shuzhi.db`，仅 `shuzhi` 用户可读写。
2. 创建 `/var/backups/shuzhi-v8530`，安装 `shuzhi-v8530-backup.timer`；服务器必须安装 `sqlite3` 命令行工具，生产 bootstrap 会先检查该依赖，缺失时禁止启动服务。
3. 首次启动前执行：

```bash
SHUZHI_ENV_FILE=/etc/shuzhi-v8530.env npm run check:shuzhi-bootstrap
npm run check:shuzhi-production-env
npm run check:shuzhi-backup-restore
```

4. 记录备份 SHA-256、`PRAGMA integrity_check` 和隔离恢复报告，在 `SHUZHI_DATABASE_ACCEPTANCE_REF` 登记。

备份脚本先写带进程标识的临时 SQLite 文件，完成完整性校验后再原子改名；巡检只认正式 `.db` 文件和同名清单，不把中途崩溃留下的临时文件当作可恢复备份。

生产订单还必须固化收货地址与经纬度。服务区域只能由后台商户管理岗位维护，不能由前台商户自行改写；每次区域变更必须带后台/机构验收证据引用，并校验区域类型、区域数组和配送方式数组。后台会在订单创建事务内重新计算供货商服务半径、当日已用单量并写入 `order_delivery_constraints`；超出半径、未配置服务区域、缺坐标或超过日单量时直接拒绝订单，不能只依赖前台的“派单预检”。采购需求发布和供货大厅直接下单均需采集收货坐标，超范围如需继续只能先由后台完成扩围审批并重新提交。

## 3. 开通微信认证

### 必须从微信侧取得

- 生产小程序/公众号的 `AppID`、`AppSecret`（只放服务端）。
- 业务域名、服务器域名和合法回调配置。
- 至少一个可核验的企业/商户测试账号，以及账号与平台主体的绑定关系。

### 联调步骤

1. 服务端配置 `WECHAT_APP_ID`、`WECHAT_APP_SECRET`、`SHUZHI_WECHAT_SESSION_URL`。
2. 用小程序 `code` 调服务端登录接口，由服务端完成 `code → session`、openid 绑定和短时令牌签发；openid 不下发前端。
3. 验收令牌刷新、退出失效、冻结/解冻和越权访问；不能用角色卡或前端传入的 `merchant_id` 代替身份。
4. 保存微信平台日志、测试用户 ID 和接口回执，在 `SHUZHI_WECHAT_ACCEPTANCE_REF` 登记。
5. 只有验收完成后才设 `SHUZHI_WECHAT_AUTH_READY=true`，并清理临时用户令牌。

## 4. 开通 CA 合同签署

CA 不是一个可由平台自行生成的密钥。需要选定合法电子签/CA 服务商，取得企业实名、证书、合同模板、摘要算法、签署回执和回调文档。

1. 取得服务商沙箱账号、出站地址、回调地址、字段字典和签名规则。
2. 实现独立 CA adapter：提交合同摘要、发起双签、查询状态、接收异步回执；回执必须验签、限时、幂等。
3. 用同一合同跑通“发起 → 双方签署 → 回执 → 摘要一致性校验 → 归档”。
4. 证书实名、摘要一致、双边回执和重复回调测试通过后，登记 `SHUZHI_CA_ACCEPTANCE_REF`。
5. 当前仓库把 CA 标为 `partial`；在具体适配器和验收完成前，不得设置 `SHUZHI_CA_READY=true`。

## 5. 开通银行/持牌支付与托管结算

### 机构侧材料

- 银行或持牌支付机构的商户号、产品/托管协议、沙箱账号。
- 统一下单、托管入金、退款、分账、争议和日终对账接口文档。
- 固定来源 IP/专线、双向证书（如机构要求）和独立回调密钥。

### 联调闸门

1. 合同双签后才能创建支付指令；订单金额以分为单位与机构回执逐分比对。
2. 入金回调只落为“已入金待验收”，不能直接分账。
3. 验收合格、发票状态满足规则、支付金额一致后才生成分账指令。
4. 退款/争议必须冻结相关款项并双人复核；同一 `Idempotency-Key` 重试不能重复扣款。
5. 平台订单、托管流水、分账流水完成日终三方对账。
6. 保存流水号、回调验签、失败重试、退款和对账证据，登记 `SHUZHI_PAYMENT_ACCEPTANCE_REF`；适配器完成前保持 `SHUZHI_PAYMENT_READY=false`。

## 6. 开通第三方物流

1. 选定承运商或聚合物流服务商，取得下单、取消、电子面单、轨迹查询和回调文档。
2. 实现独立物流 adapter：订单/批次/承运商/车辆司机/温控要求绑定后才可下单。
3. 回调映射在途、送达、异常、取消；重复回调只重放，不重复推进状态。
4. 验收真实运单号、签收回单、温度/影像索引；超温、拒收、破损必须进入人工复核并冻结结算。
5. 登记 `SHUZHI_LOGISTICS_ACCEPTANCE_REF` 后才可设 `SHUZHI_LOGISTICS_READY=true`。

## 7. 开通电子发票

1. 由实际纳税主体选定电子税务局/合规开票服务商，取得开票、验真、红冲/作废接口和授权。
2. 开票请求必须绑定订单、合同、购销主体、验收结果和金额；未验收或主体不一致时拒绝。
3. 回执验签、发票号码去重、验真结果和红冲/作废都要入账；异常不得把订单伪装成已开票。
4. 保存开票回执、验真回执和红冲测试证据，登记 `SHUZHI_INVOICE_ACCEPTANCE_REF`，再打开 `SHUZHI_INVOICE_READY=true`。

## 8. 开通监管/检测接口

1. 取得属地农业、市场监管、质检或检测机构的数据共享协议和正式字段规范。
2. 明确最小必要字段、脱敏规则、证书校验、来源 IP/专线、回执和失败补偿机制。
3. 实现独立 regulator adapter；监管回执只做留痕和状态同步，不得直接篡改交易、资金或验收结论。
4. 通过成功、超时、重复、未知批次和补偿测试，登记 `SHUZHI_REGULATOR_ACCEPTANCE_REF`，再打开 `SHUZHI_REGULATOR_READY=true`。

## 9. 逐项放行命令

每完成一项，只改对应一项 READY，并立即检查；不要一次性把全部开关改为 `true`：

```bash
SHUZHI_ENV_FILE=/etc/shuzhi-v8530.env npm run check:shuzhi-production-env
SHUZHI_ENV_FILE=/etc/shuzhi-v8530.env npm run check:shuzhi-activation
```

确认 API、数据库、微信和机构适配器都通过真实验收后，再执行：

```bash
npm run check:shuzhi-production
PRODUCTION_API_BASE_URL=https://api.你的正式域名.cn \
  CLOUD_PLATFORM_VERSION=v8533 \
  CLOUD_SERVER_RELEASE_VERSION=v8530 \
  npm run verify:production-deployment
```

最后才启动 API、机构 outbox worker 和备份 timer。首批推广建议只放行一条支付线路、一个物流商和少量已核验商户，完成一笔沙箱订单的“主体审核 → CA 双签 → 托管入金 → 发运 → 送达 → 验收 → 发票 → 结算 → 四流三账关账”全链路后再扩大范围。

## 当前必须由平台外部提供的材料

没有以下材料，仓库不能凭空生成真实能力：

- 正式域名、备案、TLS 证书和 API 服务器；
- 云硬盘/数据库、备份存储和恢复演练窗口；
- 微信生产 AppID/AppSecret、测试用户和业务域名；
- CA、银行/持牌支付、物流、发票、监管机构的合同、沙箱账号、接口文档、回调密钥和验收回执。

这些材料到位后，才是“逐一打开”；在此之前保持关闭不会影响本地演示和代码回归，也不会把不可验证的交易展示给用户。

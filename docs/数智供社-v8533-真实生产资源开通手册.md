# 数智供社 v8533 真实生产资源开通手册

本手册只描述正式环境的资源开通和验收，不把本地演示数据、演示令牌或 `CHANGE_ME` 占位值视为生产能力。当前平台前台交付版本为 v8533，后端 API 兼容发布线为 v8530。

## 0. 先确认当前实现边界

## 0.1 最短可落地路径（腾讯云）

如果目标是先让授权手机用户访问一套真实可运行的环境，建议按以下最小拓扑开通，预计先做灰度，不直接开放真实扣款：

```text
腾讯云域名（实名/备案）
        ├─ app.example.cn → EdgeOne Pages（前台 H5）
        └─ api.example.cn → CVM/轻量服务器（Nginx + API）
                              └─ TencentDB PostgreSQL/MySQL（内网）
腾讯云 SSL 证书/KMS/Secrets Manager → 证书与运行时密钥
```

开通顺序是：

1. 腾讯云注册并完成账号、域名和主体实名；大陆服务器按要求完成 ICP 备案，备案通过前可先用境外/香港节点做联调，不能把联调地址当正式生产地址。
2. 创建 EdgeOne Pages 项目绑定 `app.example.cn`，上传 `shuzhi-demo/` 整目录；创建 CVM/轻量服务器绑定 `api.example.cn`，安全组只放行 80/443，数据库只允许 API 私网地址访问。
3. 在 SSL 证书服务申请 `app.example.cn`、`api.example.cn` 证书（或使用 ACME），证书部署到 Nginx；确认 `curl -fsS https://api.example.cn/health/live` 和 `/health/ready` 均成功后，才切换前台 `VITE_API_BASE`。
4. 创建 TencentDB 实例和最小权限应用账号，完成 schema 迁移、数据校验、备份恢复演练。当前代码仍以 `SHUZHI_DB` SQLite 文件运行；未完成 PostgreSQL/MySQL repository 适配前，先按本手册的云硬盘 SQLite 试运营路线，不要误填 `DATABASE_URL`。
5. 在 KMS/Secrets Manager 生成并托管 API、管理员、五类机构回调和微信/机构密钥；服务器只通过 `/etc/shuzhi-v8530.env`（权限 600）读取，前端、小程序包和 Git 仓库绝不放密钥。

没有域名、云账号或机构授权时，任何人都不能从本地代码“生成”可用的公网 HTTPS、银行支付、CA 或微信密钥；本地只能生成随机密钥并验证配置格式，不能替代实名、备案、证书签发和机构开户。

当前 `local-backend/server.mjs` 使用 Node `node:sqlite`，生产模板的数据库变量是：

```env
SHUZHI_DB=/var/lib/shuzhi-v8530/shuzhi.db
```

API 运行时必须使用带有 `node:sqlite` 的 Node.js 版本（建议 Node.js 24 LTS；上线前在目标机执行 `node -e "const { DatabaseSync } = require('node:sqlite'); console.log('sqlite-ready')"` 验证）。不要用旧版 Node 或仅安装浏览器运行时替代 API 运行时，否则服务会在启动阶段失败。

因此，不能只把 MySQL/PostgreSQL 连接串填到 `SHUZHI_DB`；当前代码不会自动切换数据库驱动。正式规模化上线有两条路线：

* 小规模试运营：单台 API 服务器使用受保护的 SQLite 文件，配合云硬盘、备份和恢复演练；
* 正式规模化：先实现 MySQL/PostgreSQL repository 适配、迁移脚本、连接池和恢复演练，再切换流量。

无论选择哪条路线，数据库都必须放在内网，不能把数据库端口直接暴露到公网。

## 1. 域名与 HTTPS

### 手机演示的打开方式

`file:///Users/...` 是电脑本机路径，手机无法访问；把 `index.html` 单独通过微信发送也会因缺少 `assets/` 资源而白屏。手机演示只使用以下两种方式：

* 直接打开完整的单文件制品：`deliverables/数智供社-v8533/数智供社-v8533-手机演示版.html`；
* 将 `shuzhi-demo/` 目录（含 `assets/`）整体发布到 HTTPS 静态托管，不能只上传一个入口文件。

GitHub Pages 公网入口已于 2026-09-06 切换到 v8533，并完成 14 项公网回验（HTTPS、根入口、手机入口、`/shuzhi/` 兼容入口、后台入口、版本/品牌隔离和资源闭包全部通过）。每次发布后仍必须重新执行 `npm run check:shuzhi-public`，不得只以 HTTP 200 判断版本正确。

当前已回验入口：

```text
https://fywapply-jpg.github.io/gonxiang-village-demo/
https://fywapply-jpg.github.io/gonxiang-village-demo/shuzhi/
https://fywapply-jpg.github.io/gonxiang-village-demo/admin.html
```

建议为前台和 API 分配独立域名；后台先挂在前台同源的 `/admin/` 路径，避免浏览器 CORS 配置遗漏：

```text
app.example.cn             前台 H5
app.example.cn/admin/      管理后台（同源独立构建）
api.example.cn             业务 API
```

操作顺序：

1. 在正规注册商购买域名并完成实名核验；
2. 如果 API 服务器位于中国大陆，按云厂商流程提交 ICP 备案；
3. 在 DNS 中为 `api` 指向 API 服务器，为 `app` 指向静态托管或 EdgeOne；
4. 使用云证书服务或 ACME/Let's Encrypt 申请证书；
5. Nginx 监听 443，80 只做 301 跳转；
6. CORS 只允许精确的 `https://app.example.cn`，不得使用 `*`；后台使用同源 `/admin/`，不额外增加跨域来源；
7. 证书续期成功后，再启用 HSTS。

注意：EdgeOne Pages/其他静态托管只负责前台 H5、管理台和静态资源，不会自动提供业务 API、数据库或支付/物流机构通道；`api.example.cn` 仍需单独部署 API 服务器并配置证书、CORS 与健康探针。

当前 Nginx 模板：

```text
deploy/nginx-shuzhi-api-v8530.conf.example
```

API 服务器上不要手工批量替换占位域名，使用渲染器生成独立配置：

```bash
sudo npm run render:shuzhi-nginx -- \
  --api-domain api.你的域名.cn \
  --tls-dir /etc/letsencrypt/live/api.你的域名.cn \
  --output /etc/nginx/conf.d/shuzhi-api.conf
sudo nginx -t && sudo systemctl reload nginx
```

该模板只代理 API 和三个健康探针，根路径返回 404；前台 H5 与管理台继续由 EdgeOne Pages 提供，避免 API 域名误返回旧前台页面。

验收命令：

```bash
dig +short api.example.cn
curl -fsS https://api.example.cn/health/live
curl -fsS https://api.example.cn/health/ready
openssl s_client -connect api.example.cn:443 -servername api.example.cn </dev/null 2>/dev/null \
  | openssl x509 -noout -issuer -subject -dates
```

`/health/ready` 不仅检查迁移表是否齐全，还会执行 SQLite `PRAGMA quick_check`；数据库恢复未完成或一致性检查失败时，实例会返回 503，反向代理不应继续转发交易请求。

## 2. API 服务器

建议使用腾讯云 CVM/轻量应用服务器或等价的容器服务：

```text
公网 443 → Nginx → 127.0.0.1:8787 → 数智供社 API
                                   ↓
                             内网数据库
```

服务器上创建受限用户和目录：

```bash
sudo useradd --system --home /opt/shuzhi-v8530 --shell /usr/sbin/nologin shuzhi
sudo install -d -o shuzhi -g shuzhi -m 750 /opt/shuzhi-v8530
sudo install -d -o shuzhi -g shuzhi -m 750 /var/lib/shuzhi-v8530
sudo install -d -o shuzhi -g shuzhi -m 750 /var/backups/shuzhi-v8530
```

部署后使用：

```text
deploy/shuzhi-v8530.service
```

systemd 启动前会执行 `check-shuzhi-production-bootstrap.mjs` 分阶段核心门禁：拒绝演示令牌、占位配置、错误域名、危险数据库路径和未明确的能力开关。CA、支付、物流、发票、监管等未 ready 时 API 可以安全启动，但对应机构写接口仍由后端返回 503；全量推广前必须另外通过严格的 `check:shuzhi-production`。

## 3. 数据库与备份

### 3.1 SQLite 试运营路线

适用于低并发、单实例、可控订单量的首批灰度：

* 数据库文件放在独立云硬盘；
* 只允许 `shuzhi` 用户读写；
* 不把 `.db` 放入 Git 或静态发布包；
* 每日备份，保留至少一份异地备份；
* 每次发布前备份；
* 每月至少一次恢复到临时库并读取组织、商户、订单、合同、支付、物流、发票、审计表；
* 发生资金或主体异常时先停止写入和回调消费，再恢复到已验证备份。

### 3.2 MySQL/PostgreSQL 正式路线

在腾讯云购买 TencentDB 或同类托管数据库，并配置：

* 私有网络连接；
* 仅 API 安全组可访问；
* 独立应用账号，不使用 root；
* 自动备份和按时间点恢复；
* 高可用/只读副本按 SLA 配置；
* 慢查询、连接数、磁盘和备份失败告警。

切换前必须完成：schema migration、数据迁移校验、双写或停机切换方案、回滚方案和恢复演练。没有完成适配前，不能把 `DATABASE_URL` 当成已生效的生产配置。

## 4. 密钥与令牌

先区分三类信息：

* GitHub 账号是登录用户名或邮箱，用于判断是否有仓库写入权限；
* `AppID`、商户号等是应用标识，不等于密码，仍应限制传播范围；
* `AppSecret`、访问令牌、数据库密码、证书私钥和回调密钥是秘密，不能用来代替 GitHub 账号，也不能通过聊天提供。

已经出现在聊天、工单、截图或公开文件中的密钥一律视为泄露：先在原平台撤销，再生成新值。新值只写入云 Secrets Manager/KMS 或服务器的受限环境文件，不回填到文档。

在服务器或云密钥管理服务中生成，不在聊天、前端代码、GitHub 或小程序包中保存：

```bash
openssl rand -hex 32
```

至少分别生成：

```text
SHUZHI_API_TOKEN
超级管理员、运营、审核、财务、客服令牌
采购商和供货商临时会话令牌（微信认证 ready 后删除）
LOGISTICS_WEBHOOK_SECRET
PAYMENT_WEBHOOK_SECRET
INVOICE_WEBHOOK_SECRET
REGULATOR_WEBHOOK_SECRET
WECHAT_APP_SECRET
CA/支付/物流/发票机构的正式凭证
```

CA、支付、物流、发票、监管五类回调密钥不能共用。回调签名使用时间戳和原始请求体，密钥至少 32 字符；定期轮换时保留短暂的旧密钥验证窗口，并记录审计事件。

正式微信认证完成后，建议清空 `SHUZHI_USER_TOKEN_PRINCIPALS` 中的长期静态用户令牌，让用户统一通过 `code → session` 获取短时会话；微信认证尚未 ready 时，才保留临时用户令牌用于受控联调。

提交或发布前执行：

```bash
npm run check:secret-hygiene
```

检查器只输出风险文件名和凭据类型，不打印匹配到的值；Pages 发布工作流也会在上传制品前自动执行该检查。

推荐保存位置：腾讯云 KMS/Secrets Manager，或权限为 600 的服务器文件：

```text
/etc/shuzhi-v8530.env
```

## 5. 生产环境变量映射

从模板复制后只在服务器受限文件中填写真实值：

```bash
sudo cp deploy/shuzhi-v8530.env.example /etc/shuzhi-v8530.env
sudo chmod 600 /etc/shuzhi-v8530.env
SHUZHI_ENV_FILE=/etc/shuzhi-v8530.env npm run check:shuzhi-production-env
```

也可以在服务器上用初始化工具生成随机令牌和五类独立回调密钥（默认拒绝覆盖已有文件）：

```bash
sudo npm run create:shuzhi-production-env -- \
  --output /etc/shuzhi-v8530.env \
  --app-domain app.example.cn \
  --api-domain api.example.cn
sudo chmod 600 /etc/shuzhi-v8530.env
```

工具不会生成或猜测微信、CA、支付、物流、发票和监管凭证；生成后仍须由账户所有者填写真实值，再运行生产变量检查器。轮换令牌时先备份旧文件，并显式追加 `--force`。

关键项：

```env
SHUZHI_RUNTIME_MODE=production
SHUZHI_DEPLOY_ENV=tencent-prod
SHUZHI_SERVICE_NAME=shuzhi-v8530
SHUZHI_PLATFORM_VERSION=v8533
SHUZHI_RELEASE_VERSION=v8530
SHUZHI_ALLOWED_ORIGIN=https://app.example.cn
VITE_API_BASE=https://api.example.cn
```

`VITE_API_BASE` 只填写 API 根地址，不要附加 `/api`。生产构建禁止配置 `VITE_API_TOKEN` 或 `VITE_ADMIN_TOKEN`。

微信、CA、支付、物流、发票和监管能力只有在真实机构完成合同、白名单、密钥、回调、幂等、失败重试和对账验收后，才能分别设置为 `true`；禁止为了通过门禁直接改值。

支付特别说明：当前前台只有本地演示环境允许模拟支付结果；正式构建不会用定时器或本地状态返回“支付成功”，未完成支付机构统一下单、客户端支付参数和异步回调联调时会明确提示“未执行扣款”。生产上线必须先完成机构支付联调，再把 `SHUZHI_PAYMENT_READY` 置为 `true`。

## 6. 放行顺序

### 6.1 先启动核心 API，再逐项开通能力

首次部署或只开放部分能力时，先运行分阶段门禁：

```bash
SHUZHI_ENV_FILE=/etc/shuzhi-v8530.env npm run check:shuzhi-bootstrap
sudo systemctl enable --now shuzhi-v8530.service
```

分阶段门禁要求 HTTPS、生产数据库/备份目录、内部岗位认证和明确的 `READY` 布尔值；微信未 ready 时必须使用受控临时会话令牌，机构能力未 ready 时不要求猜测服务商地址或密钥。它不会放行任何未 ready 的 CA、托管支付、物流、发票或监管写操作。

每开通一个能力，先完成该机构的合同、白名单、字段适配、签名、回调、幂等、失败重试和对账验收，再填写对应 `SHUZHI_*_READY=true` 和验收证据编号，然后重新运行：

```bash
SHUZHI_ENV_FILE=/etc/shuzhi-v8530.env npm run check:shuzhi-activation
SHUZHI_ENV_FILE=/etc/shuzhi-v8530.env npm run check:shuzhi-production-env
```

全部能力都完成后，才执行严格全量放行：

```bash
SHUZHI_ENV_FILE=/etc/shuzhi-v8530.env npm run check:shuzhi-production
```

在逐项申请外部资源时，先运行能力开通诊断。它不会显示任何密钥，也不会自动把
`READY` 开关改成 `true`：

```bash
SHUZHI_ENV_FILE=/etc/shuzhi-v8530.env npm run check:shuzhi-activation
```

诊断结果会区分“配置未完成”“待真实联调验收”“待实现机构适配器”和
“危险：开关已开但适配器不完整”。当前微信 `code → session` 已有完整后端接线；
CA、支付、物流、发票和监管目前只有部分内部状态机或入站回调能力，仍须按所选
机构的正式 API 实现独立出站适配器。仅填写回调密钥或修改 `SHUZHI_*_READY=true`
不代表已经具备生产能力。

五类机构统一接入契约见：

`docs/openapi/数智供社-v8533-机构适配协议-v1.openapi.json`

该契约把平台命令与机构回调分开：所有出站写命令必须携带
`Idempotency-Key`，平台出站和机构回调分别使用独立时间戳、签名和命令/事件号；
HTTP `202` 只代表“已受理”，最终状态必须由验签回调推进。选定具体服务商后，
只在独立适配器中转换服务商字段，不允许修改小程序 BFF 的订单 DTO 或绕过现有
订单、验收、发票和结算状态机。

平台侧统一出站客户端位于 `institution-adapters/shared/client.mjs`，已经强制 HTTPS、
独立 HMAC 密钥、500—30000 毫秒超时、禁止重定向、16—128 字符幂等键和统一
`202 + code=0` 响应校验。它只负责安全协议，不包含任何机构业务字段猜测；选择
服务商后应在该客户端之外新增单独的字段转换器，并执行：

```bash
npm run check:shuzhi-institution-client
```

跨数据库事务与外部 HTTP 的一致性由 `institution-adapters/shared/outbox.mjs` 和
`worker.mjs` 处理。业务操作必须先在同一个本地事务中写入 `institution_outbox`，
提交后再由工作进程投递；失败按指数退避重试，超过上限转为死信，不允许业务接口
因为 HTTP 超时直接重复改变订单。系统管理岗位可通过
`GET /api/v1/admin/institution-outbox` 查看汇总和脱敏列表，通过
`POST /api/v1/admin/institution-outbox/:id/retry` 对审核后的死信进行重放。执行：

```bash
npm run check:shuzhi-institution-outbox
```

Outbox 的 `accepted` 只说明机构接收指令，合同、资金、物流、发票和监管最终状态仍须
由验签回调推进。完整流程冲突台账见
`docs/数智供社-v8533-真实运营全流程冲突审计-2026-09-06.md`。

```text
域名/备案 → TLS/CORS → API健康检查 → 空生产库 → 备份恢复
→ 微信身份 → CA合同 → 托管支付 → 物流 → 发票 → 监管
→ 沙箱端到端订单 → 一条线路灰度 → 正式推广
```

商户入驻还必须经过独立事实核验：审核员通过入驻资料后，商户仍保持
`license_status=pending`、`bank_status=pending`；审核岗位需调用
`POST /api/v1/admin/merchants/:merchant_id/verification` 写入核验机构和证据引用，
营业执照与对公账户均为 `verified` 后，运营岗位的启用接口才会放行。这样不会把
“资料审核通过”误当成工商或银行已经核验。核验时还要提交 18 位统一社会信用代码；
平台写入 `merchant_identity` 后，支付、物流、发票和 CA 指令会逐字核对备案代码，
错配直接返回 409，不会把其他主体的代码发送给外部机构。

执行：

```bash
npm run check:shuzhi-production
npm run check:shuzhi-startup
npm run check:shuzhi-backup-restore
npm run verify:production-deployment
```

API 服务之外还必须启动机构 Outbox 工作进程（同一 `SHUZHI_DB`、同一环境文件）：

```bash
sudo systemctl enable --now shuzhi-v8530.service
sudo systemctl enable --now shuzhi-v8530-institution-worker.service
sudo systemctl status shuzhi-v8530-institution-worker.service
```

工作进程只接受生产模式，并要求五类机构各自的 `SHUZHI_*_ADAPTER_URL` 与
`SHUZHI_*_ADAPTER_SECRET`。它不会把机构 HTTP `202` 当成业务完成；失败按指数退避，
超过最大次数进入死信，须由系统管理岗位审核后调用后台重放接口。API 和工作进程
不得各自使用不同数据库，否则会出现“前台已下单、工作进程看不到指令”的运营事故。

采购付款页在正式环境调用 `POST /api/v1/trades/{order_id}/pay` 创建托管入金指令；
该接口只返回机构受理状态，前台必须等待支付回调后才能展示“已入金”，禁止把按钮点击
或 HTTP 202 当作扣款成功。支付回调还必须携带机构交易号和金额，平台只保存对账事实，
不经手交易货款。

静态托管发布后，用公网版本回验防止“HTTP 200 但仍是旧版”：

```bash
SHUZHI_PUBLIC_BASE_URL=https://你的域名/项目路径 npm run check:shuzhi-public
```

该检查会读取根入口、`app.html`、`/shuzhi/app.html` 和 `admin.html`，核对 v8533、历史品牌隔离以及手机入口资源闭包。

微信开发者工具预览包的可复现打包顺序：

```bash
npm run build:shuzhi-mp
npm run build:shuzhi-mp-preview-zip
```

如果是正式小程序构建，先以真实 HTTPS API 根地址执行 `npm run build:shuzhi-mp-production`，再执行同一个 ZIP 打包命令。打包脚本会同时更新根目录兼容下载文件和 `deliverables/数智供社-v8533/` 归档文件。

H5 发布前使用受控同步脚本，避免把上一次构建遗留的哈希资源一并上传：

```bash
VITE_API_BASE=https://api.你的域名.cn npm --prefix work/shuzhi-v8502-source run build:h5:production
npm run sync:shuzhi-h5
npm run build:v85-singlefile
npm run build:shuzhi-pages-zip
```

`sync:shuzhi-h5` 只同步当前生产构建的 `assets/` 与 `static/`，并清理 `shuzhi-demo/assets/` 中的旧哈希文件；同步后仍须执行发布完整性和公网回验。

只有生产检查 0 失败、机构能力全部 ready、公网 HTTPS 回验通过，才允许打开真实交易入口。

## 7. 不能交给聊天完成的事项

域名注册、ICP备案、云账号实名认证、微信 AppSecret、支付机构密钥、CA 私钥和数据库密码都属于你的账户或机构凭证。它们必须由账户所有者在云控制台或密钥管理服务中创建和授权；不要把这些秘密发到聊天中。

# 数智供社 v8533 生产边界审计（2026-09-07）

## 审计结论

本轮审计针对当前正式交付线（前台 v8533、后端 API v8530）检查了前台静态样例回退、支付结果伪造、移动管理页与后台数据边界、HTTPS API 会话令牌边界，以及交易/采购大厅已有的主体、资金和履约闸门。

结论：**代码边界可以继续进入外部机构灰度联调；尚不能宣称正式生产交易已经开通。** 当前未配置真实生产 API 地址、数据库恢复证据、微信生产认证验收和 CA/支付/物流/发票/监管机构的正式适配与回执，因此真实资金、合同、履约和监管写操作继续保持后端关闭或待机构确认。

## 本轮已修复

- 订单农业结算页、信誉收益页、行情指数页在正式构建中不再展示固定合同、价格、评分、收益或行情样例。
- 支付结果页不再信任 URL 中的 `ok`、`amount`、`trade` 参数；正式环境只能显示“等待后台/持牌机构回执”。
- 移动端管理中心、数据看板、区域管理、权限设置和 DID 页面不再展示静态管理员、区域、经营指标、凭证或权限矩阵；生产管理回到独立后台。
- 指向 HTTPS API 的开发联调构建也不再回退发送 `local-demo-token`，避免误连正式 API 时混淆会话边界。
- 生产验收接口新增物流送达门禁：所有关联运单必须由物流机构回调确认为“已送达”且无异常，才允许形成最终验收结论；送达前不能进入开票和结算链路。
- 生产环境的 `accepted` 验收必须按 `order_items` 逐项提交 `accepted_items`，每项数量与订单明细一致；不同计量单位不得简单相加，部分到货不得直接标记为全量合格，必须提交争议并冻结差异，不能提前开票或结算。
- 本次新增的 `acceptance_items` 不会为历史“只有总量验收”的记录自动补证据；升级后历史未关账订单必须由采购验收岗重新按明细核验，不能用脚本回填或绕过逐项门禁。
- 统一农资采购方（`agri`）与普通采购商的需求列表、直接建单和主体校验，避免农资采购方能发布需求却无法完成交易。
- 生产业务工作流推进改为要求后台“数据管理”写权限；只读财务/审核岗位不能通过通用工作流接口改变状态，后台界面同步隐藏生产环境的一键推进/重置误导操作。
- 交易流程组件和公开交易配置在正式构建/API 中不再展示固定示例订单金额或平台费；生产金额统一读取后台订单明细和机构回执。
- 服务半径不再只是前置查询：服务区域改由后台商户管理岗位维护，区域变更绑定验收证据且严格校验类型/数组字段；生产采购需求必须采集收货坐标，正式订单创建事务重新计算供货商距离、日单量并写入 `order_delivery_constraints`；缺坐标、超半径、无服务区域或超日单量均被后端拒绝。
- 生产 API 启动门禁继续下沉到后端自身：非 HTTPS 根 CORS 来源、以及已声明 READY 但没有 HTTPS 机构适配器根地址的配置会直接拒绝启动，避免绕过 bootstrap 检查后形成“服务已起但机构出站不可用”。
- 备份流程改为临时文件完成 `integrity_check` 后原子发布，并保留毫秒级文件名，降低崩溃半成品和同一秒覆盖风险。
- 供货大厅直接下单和采购大厅按报价下单均已接入收货地址/坐标字段；前台地图选点只是采集入口，最终判定仍由后台完成。
- 交易状态机补齐终态门禁：已取消交易不得继续签署合同、登记运单、提交验收或接受 CA/物流/支付/发票机构回调；已完成或已关账交易不得新增运单、验收和发票，避免取消、退款、开票、结算之间形成账本分叉。
- 生产资金与履约前置顺序补齐：合同双方完成 CA 双签前，生产接口不得发起托管入金或登记运单；本地演示仍保留离线跑通能力，生产回归覆盖 CA 回执后才放行后续节点。
- 对预付款/机构监管结算模型增加资金前置门禁：托管资金尚未取得机构确认时不得登记生产运单；货到即付等后付模型仍按其对应合同规则执行。
- 退款状态与发票状态相互隔离：退款待受理、处理中、部分/全额退款或退款失败时，生产普通开票被阻断，必须先财务复核或走红冲流程，避免全额蓝票与退款账本冲突。
- 分账金额一致性补齐：生产开票、发票机构回调、最终结算和支付机构分账回执同时核对订单、托管支付、发票三方金额，均按人民币分校验；任一金额不一致时拒绝开票或关账。
- 机构分账流水号增加跨交易唯一约束：同一机构流水号或结算指令号如果已绑定其他订单，支付回调和财务结算均返回业务冲突，不再让数据库唯一键异常代替业务判断。
- 商户核验计数改为按 `license`/`bank` 类型去重，重复提交同一类证据不能冒充另一类核验；生产启动和交易主体门禁使用同一规则。
- 生产启动与交易主体门禁进一步统一：`license`/`bank` 核验记录必须同时具备机构、证据引用和 `verified_at`，空证据记录会在启动阶段被拒绝，不再出现“服务已启动但主体不可交易”的假 ready。
- 以上修复不改变本地演示模式；本地演示仍可按原流程运行。

## 正式放行仍缺的外部证据

1. 正式域名、备案、TLS 证书、API 服务器和真实 `PRODUCTION_API_BASE_URL`；
2. 云硬盘/托管数据库、备份 SHA-256、`integrity_check` 和隔离恢复报告；
3. 微信生产 AppID/AppSecret、业务域名、测试主体及 `code → session` 验收；
4. CA/电子签服务商的字段适配、双签回执和证书验签证据；
5. 银行/持牌支付机构的托管入金、退款、分账、争议和日终三方对账证据；
6. 物流、发票、监管/检测机构的正式协议、测试账号、回调密钥、字段适配和失败补偿验收。

缺少其中任一项时，不得仅修改 `SHUZHI_*_READY` 绕过门禁。逐项开通步骤见[逐项开通操作卡](./数智供社-v8533-逐项开通操作卡.md)，部署拓扑和环境边界见[真实生产资源开通手册](./数智供社-v8533-真实生产资源开通手册.md)。

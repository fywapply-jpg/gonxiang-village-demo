# 供享村社三项软件著作权代码归属清单（第一版）

> 基准版本：供享村社 v3.1009  
> 目的：先划清三套软件的真实代码边界，再制作源代码鉴别材料和使用说明书。  
> 原则：不为凑页数新增无意义代码；不提交 `node_modules`、第三方框架源码和无授权素材；同一业务文件只设一个主归属。

## 一、总体盘点

- `src` 下共 316 个文件。
- TypeScript / TSX / CSS 等自有代码约 21,038 行。
- 共富候选代码约 3,221 行。
- 公益核心候选代码约 1,198 行；加入真实相关服务、授权和公共运行代码后可组成完整鉴别材料。
- 党建候选代码约 3,020 行。
- 三项均具备形成独立源代码材料的基础，但公益和党建各有少量“页面能演示、跨角色数据未完全贯通”的地方，正式出材料前应做一次最小硬化。

## 二、软著一：供享村社全民共富权益核算与分配管理软件 V1.0

### 1. 独立功能边界

成员资格与权益确权、社会贡献值计算、贡献值有效期、共富分配规则、利益共同体、交易分账测算、年度分红、专项基金、盈亏平衡、个人权益资产和公示审计。

### 2. 主归属文件

| 模块 | 主文件 |
|---|---|
| 共富分配制度与交互测算 | `src/pkgPlatform/prosperity/index.tsx`、`index.css` |
| 利益共同体 | `src/pkgPlatform/interest-community/index.tsx`、`index.css` |
| 支付结算与分账规则 | `src/pkgPlatform/settlement/index.tsx`、`index.css` |
| 盈亏平衡计算器 | `src/pkgPlatform/breakeven/index.tsx`、`index.css` |
| 个人权益与经营资产 | `src/pkgPlatform/my-assets/index.tsx`、`index.css` |
| 全生命周期贡献 | `src/pkgPlatform/lifecycle/index.tsx`、`index.css` |
| 信用与数字权益 | `src/pkgPlatform/credit/index.tsx`、`src/pkgPlatform/digital-asset/index.tsx` 及对应样式 |
| 社会贡献值账户 | `src/pages/contribution/index.tsx`、`index.css` |
| 贡献申报与审核 | `src/pkgLife/contrib-submit/`、`src/pkgLife/contrib-audit/` |
| 贡献模型说明 | `src/config/contribution-model.ts` |

### 3. 数据层归属

从 `src/store/index.ts` 中抽取以下业务段，不整份重复提交：

- `ContribDimKey`、`ContribDimension`、`ContribRecord`、`ContribAccount`；
- 贡献值初始维度、时间戳记录、等级计算；
- `getActiveContrib`、`getExpiredContrib`、`getExpiringContrib`；
- `getSpendable`、`spendContrib`、`restoreContrib`；
- `addContribution`、`reviewContrib`、`addContributionAuto`；
- 订单贡献值确认与退款冲正方法。

### 4. 当前代码量判断

候选 TS / TSX 约 2,375 行，加对应 CSS 后约 3,221 行，已经达到制作60页代码鉴别材料的基本规模，无需制造填充代码。

### 5. 出材料前只做三项必要核验

1. 核对“平台技术服务费2%、且不超过毛利12%”在所有页面表述一致。
2. 区分制度展示、测算结果和真实银行划款，说明书不得把测算写成已完成资金存管。
3. 用固定测试参数验证贡献值有效期、分红比例和盈亏平衡公式。

### 2. 主归属文件

### 3. 数据层归属

从 `src/store/index.ts` 中抽取公益专属业务段：

- `CharityPerm`、`CharityClaim`、`CharityItem`、`CharityOrg`；
- `VolPost`、`VolRecord`、`VolCert`、`VolLevel`；

### 4. 当前代码量判断

公益主程序及直接页面约 1,198 行；相关关爱、青少年、审批、隐私页面合计约 2,003 行。再加入公益专属数据层与最少运行入口后，可形成超过3,000行的连续材料。不得用无关商城代码凑页数。

### 5. 出材料前只做三项必要硬化

1. 管理权限必须只认真实角色和已授权机构，不能由网址参数直接获得管理员权限。
2. 机构、项目、捐赠、志愿记录在不同角色切换后应读取同一份持久数据。
3. 说明书中的“票据、上链、国家机构审核”区分真实接入与演示能力，不作超出现状的表述。

2. 微心愿“发布—认领—办结”使用同一记录，贡献值只在约定节点产生一次。
3. 地图点位、组织名称和行政区划必须来源清楚，演示组织不得写成真实授权单位。

## 五、三套软件共用但不设主归属的文件

以下属于运行基础，可在各套鉴别材料中保留最少必要部分，但不得整包重复：

- `src/app.tsx`
- `src/app.config.ts`
- `src/config/version.ts`
- `src/config/region.ts`
- `src/config/sections.ts`
- `src/components/TabBar/`
- `src/store/index.ts` 中的登录用户、角色和通用存储部分

处理方式：制作材料时按业务抽取 `store` 代码段，并在每套材料首页注明软件名称、版本和模块范围，不把同一份773行总仓库文件原样复制三次。

## 六、明确排除

- `node_modules/` 和 Taro、React、Leaflet、XLSX 等第三方库源码；
- 构建产物 `dist/`、`dist-h5/`；
- 与三项软件无关的商城商品图片和测试缓存；
- 没有商用授权证明的字体、图标、地图底图；
- 仅存在于宣传文案、没有代码实现的银行存管、真实上链和真实电子发票能力。

## 七、下一步验收标准

1. 为每项生成一份“文件—功能—代码行数—是否持久化—是否演示”的明细表。
2. 三项核心业务文件主归属不重复。
3. 每项可选出不少于3,000行连续、可读、与功能一致的源代码。
4. 对上述必要缺口只做最小修复，并通过编译及对应业务流程测试。
5. 代码边界确认后，再生成三份源代码 Word 和三份使用说明书。
